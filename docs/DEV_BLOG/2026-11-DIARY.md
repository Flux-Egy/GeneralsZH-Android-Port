# November 2026 Development Diary

## 03/11/2026 -- Flux Build v1.3.8-test1 (diagnostic test build)

Test build (`versionCode 12119`, `versionName 1.3.8-test1`, update channel `test`), both games,
both tick rates. It carries the fixes below and a temporary `[gxtread]` trace for the tank treads.

### Mod mount order: mods over the community patch, and inside a mod the first name wins

- Inside one launcher-managed mod the archive whose **file name** sorts first wins again -- the retail
  rule for archives in the game folder, and the one mod authors name their files for (Rise of the Reds:
  `!Rotr_*`, `!!Rotr_*`, `!!!Rotr_*`, `!!!!!!!!Hanpatch_*`, each extra `!` one step higher). v1.3.1
  (5d776a6e) had switched to ascending order, so the alphabetically last archive won and a mod's base
  overrode its own patches. Sorted by file name rather than path, so an archive in a subfolder of the
  mod keeps the priority its name gives it. `!!loose_files.big` stays on top.
- The community patch is never inserted ahead of a launcher-managed mod archive
  (`loadIntoDirectoryTree`, sorted-by-name branch). With "patch with mods" switched on, the patch used
  to override every mod archive whose name sorts after `500_900_`.
- Unchanged: the patch stays out whenever an enabled mod carries game data.
- The log now prints each managed archive's mount position (`[gxbig] mod mount N of M`).

### Hotkeys: installer, in-app editor

- `HotkeyPackInstaller` replaces both old importers (Settings and the Mods screen). Files go where the
  engine reads them: `.csf` to `Data/<game language>/` (unit, building and power hotkeys are the `&`
  letter of each button label, `HotKeyManager::searchHotKey`), `.ini` to `Data/INI/` keeping sub-paths,
  `.wnd` to `Window/`, `.big` to the game folder with a `!`. Unit and rule INIs are refused (they would
  change the INI checksum and mark the install as modded). Every replaced file is backed up to a
  manifest in app storage; Restore undoes exactly that. Runs off the UI thread. The Mods screen now
  recognises a hotkey pack before packing loose files (it used to install one as a disabled mod).
- The old restore deleted every game-folder file with "ControlBar" in its name; gone.
- `HotkeyEditorActivity` edits 26 common commands of the game's command map. Defaults are read from
  the game's language archive (`Data\<language>\CommandMap.ini` in e.g. `EnglishZH.big` -- the
  `Data\INI\CommandMap.ini` in `INIZH.big` is a 249-byte stub). Only changed commands are written, as a
  loose `Data/INI/CommandMap.ini`, which the engine loads over the language file entry by entry.
  Conflicts are flagged; a hardware keyboard can pick the key. Not part of the INI checksum.
  Attack Move, Guard, Scatter, Deploy and General powers are control-bar buttons (keys from
  `generals.csf`), not command-map entries; the editor says so.

### Launcher

- Render scale is back on every GPU (v1.3.7-hotfix hid it on Mali/Xclipse/PowerVR); only the GSR
  sharpening switch is Adreno-only (`GXUpscaler = bilinear` elsewhere). `Options.ini` is written only
  when the filter value changes, no longer on every Graphics-page open.
- `InsetUtil` pads for the on-screen keyboard (enforced edge-to-edge on Android 15 no longer resizes).
- Gesture help on the Mobile Controls card (text only; touch code untouched).
- 13 hard-coded toasts moved to `strings.xml`; 180 strings machine-translated into all 12 locales,
  applied only where the locale still had the English copy (existing translations kept). To review.

### `[gxtread]` trace (temporary)

Source review found every link of the tread scroll correct (W3DTankDraw offset -> material override
-> LinearOffset mapper -> DX8Wrapper transpose -> d3d8gles transform -> program key -> uTexMat upload
-> `(u, v, 1, 0)`), and the v1.3.7-hotfix engines all contain the shader fix. The trace logs, rate
limited, the tread meshes each tank finds, the scroll branch inputs while moving, whether a tread mesh
takes the sorted path (where the offset is never applied), and the texture-stage state and matrix of
the GLES draw that follows. To be removed with the fix.

## 03/11/2026 -- Flux Build v1.3.8-test2 (unit and building hotkey editor, control bar ZIP)

### Unit & Building Hotkeys (GenHotkeys-style)

  (`HotKeyManager::searchHotKey`; `CONTROLBAR:ConstructAmericaPowerPlant` = "Cold Fusion &Reactor").

  on the host; with Shockwave: 15 factions, 474.
- `UnitHotkeyEditorActivity`: faction -> units and buildings by group -> buttons -> key grid (A-Z,
  0-9; keys of the unit's other buttons in red, the game's command-map keys listed). Clashing keys
  are flagged per unit, with a filter. A label shared by many units (Attack Move, Guard...) says so.
- The key goes in front of that letter where the name has it (word start first), else as " (&X)" --
  the language packs' style for other scripts. Saved as a loose `Data/<language>/generals.csf` with
  only the changed labels (and a marker naming them): GameText reads a loose table first as a mod
  table; labels it lacks fall back to the game's or the mod's own text. A hotkey pack's loose table is
  kept in the written one and restored by Reset (`HotkeyPackInstaller` backup).

## 05/11/2026 -- Workflow tooling (no game change)

Build and test tooling for the v1.3.8 finalization; nothing in the APK changes.

- **ccache**: the build's cache (`CCACHE_DIR=~/.cache/ccache`) had no `sloppiness`, so ccache refused
  every compile that used a precompiled header (1738 of 1950 calls, "Could not use precompiled
  header"). `build-local-sandboxed.sh` now sets `sloppiness=pch_defines,time_macros`; an isolated
  test confirmed hits with the same PCH flags. To be measured on the next full build.
- **Same-tree check and engine stamp**: `engine-fingerprint.sh` hashes the engine sources (Core,
  Generals, GeneralsMD, Dependencies, CMake, vcpkg manifests, the build scripts) as they are in the
  working tree. `build-dual-hz.sh` takes it before pass 1 and after pass 2 and fails if it moved (two
  engines from different trees), then writes `build/engines.stamp` with the fingerprint and the four
  engines' sha256.
- **`repackage-launcher.sh`**: for a launcher-only change, packages a new APK around the stamped
  engines in about half a minute. Refuses if the fingerprint or an engine hash differs from the
  stamp, and checks the four engines inside the finished APK.
- **Symbol tables**: `build-dual-hz.sh` now always keeps the unstripped symbols of all four engines in
  `build/symbols/<versionName>/` (the two newest builds), for symbolizing testers' tombstones.
- **`scripts/qa/adb-test.sh`**: install (asks first, by convention) / launch / pull logs and the
  crash buffer / screenshot / screen recording for `com.generalsx.flux.dev`, into `logs/device-*`.
- **`scripts/qa/logtriage.py`**: one-pass summary of a device log with `[GX-NET]` hidden (build,
  mod mount order, string tables, fps percentiles, collapsed warnings), `--tag`, `--grep`,
  `--tread` (the `[gxtread]` checks) and `--diff` between two logs. On the test1 match log
  (300k lines): 0.3 s.
- **`.clangd`**: clangd reads `build/android-vulkan/compile_commands.json`, so engine files are
  analysed with the real NDK flags and defines.
- **`.claude/agents/`**: two read-only reviewers, `engine-reviewer` (lockstep/CRC, memory
  ownership, render-thread races) and `launcher-reviewer` (UI-thread I/O, 13 locales, game-folder
  safety).

## 05/11/2026 -- Flux Build v1.3.9-test1 (map previews, hotkey packs named ...ZH)

### Custom maps had no preview in the lobby

`getMapPreviewImage` copies a map's preview into `<user data>/MapPreviews/` under a name built
from the map's portable path, turning `\` and `:` into `_`. A custom map's portable path keeps the
native `/` in its folder part (`userdata\maps\arabia v2/arabia v2`), so the copy was aimed at a
subfolder of MapPreviews that does not exist, failed, and the lobby showed nothing. On the test
phone all 53 copies in MapPreviews were `maps_...` (archive maps); none of the 82 maps in the user
Maps folder had one, though most ship a `.tga`. `/` is flattened too now (MapUtil.cpp, client
side only).

### Hotkey packs named without ".big"

Hotkey and interface packs circulate as BIG archives named `!HotkeysLeikezeZH` (no extension) or
`*.zh`. The engine only ever listed `*.big`, so such a file did nothing. Now
`ArchiveFileSystem::addRenamedBigArchives` adds files with no extension or `.zh` that start with a
BIGF/BIG4 signature to the same sorted list as the `*.big` (game folder: that folder only; mod
folders: recursively), so they mount under their own names in the usual name order. Nothing is
renamed, by the engine or the launcher.

The name decides nothing else: whether an archive is a gameplay mod is still read from its content
(gxIsDataModArchive). Samples:
- `!HotkeysLeikezeZH`: one entry, `Data\English\generals.csf`. Not a mod; its labels win as a mod
  table (`!` prefix) and override a language pack's.
- `!HotkeysLeikezeIndicatorsZH`: 12 UI textures, 4 MappedImages INIs and
  `Data\INI\CommandButton.ini`. CommandButton.ini is not in the INI checksum (ControlBar loads it
  without one), but a `!` archive with any Data\INI file counts as a gameplay mod here, so the
  community patch stays off -- and the patch's INI is checksummed, so online this install no
  longer matches unmodded Android players. The launcher now says so on import
  (`hotkeys_import_gameplay_archive`). Note that a copy already in the game folder is mounted
  from this build on, imported or not.

Launcher: one rule for "an archive the engine mounts" (`BigArchive.isMountedArchive`), used by the
hotkey and control bar importers, the Mods screen import and packing, mod analysis, the data-mod
finder and both editors.

### Hotkey editor and lower-case label tables

Leikeze's `generals.csf` spells all 6422 labels in lower case (`object:ranger`). The engine matches
labels without case; the Unit & Building editor did not, so with that pack visible it would have
listed no unit at all. Its label maps are case-insensitive now. Checked off-device against the
phone's game folder (read-only) with both packs in it: 453 units, 262 button labels, every letter
the pack's (225 differ from retail, e.g. Raptor T -> F, Comanche C -> D).

### Control Bar Pro ZIP

`ControlBarProZH_v1.0.3...zip` (ExiLe edition) was already handled: its two archives install as
`00CB_340_ControlBarPro1080ZH.big` / `00CB_340_ControlBarProZH.big`; the optional `.big.bak`
toggles (hide IP / e-mail) and the ReadMe are skipped. It is made for GenTool, which picks the

### Review (engine-reviewer, launcher-reviewer) before the build

- Only the BIGF signature counts as a renamed archive (engine and launcher): the loader refuses
  BIG4, so a renamed BIG4 would have been reported installed and never mounted.
- A folder whose only archive is a renamed one no longer passes for an asset folder: the asset-root

  mounted.
- The editor's index takes renamed archives from the game folder only, as the engine does (one
  folder down it mounts `*.big` only).
- The Mods screen texts that list formats (`mods_import_rar`, `mods_library_empty`) and the control

- Left as they are: a renamed pack without a leading `!` keeps its name (no renaming, by request),

  archives reach Zero Hour as before (now also renamed ones); `-mod <dir>` appears to mount nothing

### Camera & Selection Mode (touch)

Box selection felt slow: a one-finger drag pans, and became a box only after the finger had been
still for 400 ms (BOX_HOLD_MS). The 160 ms force-select is a different gesture (release on your own
unit) and was not the delay. The launcher now offers two schemes, `GXSelectionMode` in Options.ini
(SDL3Main.cpp -> GX_SELECTION_MODE -> SDL3GameEngine.cpp):
- 1, Classic (default): as before, hold shortened to 160 ms; the ring shows after 80 ms.
- 2, Two-finger: no hold; two fingers move, zoom and turn the camera. A one-finger drag becomes a
  box once it has gone 24 px along one axis (the selection translator's own test, so the box really
  exists) and 80 ms have passed since touch-down. Once begun, a box can only end as a box: every raw
  release becomes a click with the anchor-to-release region (MetaEvent.cpp). So it must not begin
  while a second finger may still be on its way. Inside the 80 ms a second finger starts the camera
  gesture with nothing sent, and a drag lifted inside it is dropped, not turned into a tap. (A first
  version started the box at once and tried to abandon it when the second finger landed; review
  showed the release still selected, or ordered, and could leave the drag lock stuck. Replaced.)
- Both modes: a drag that starts on the interface (minimap, panels) pans and sends no button. On
  the minimap with units selected a left button down is a move order, and the shorter hold would
  have made that easy to trigger.

## 05/11/2026 -- Flux Build v1.3.9-test6 (measurement build + Performance Guard)

### Measurement build (the audit's step 1)

The audit of the test1 match log (460 reports) found the slowest frames waiting ~15x longer on the
render thread (sync 3.25 vs 0.21 ms/frame), the render thread busy 12-16 of 16.7 ms (uploads
4.3-5 ms, ~4 MB of commands a frame), the shader cache saving nothing (save=0 throughout, 28 builds
in 107 ms at one match load), 570-730 untagged draws a frame, and the UI text renderer creating
most mid-match textures (Render2DSentenceClass::Build_Textures). Before changing any of it, this
build measures what the log could not say:
- `[d3d8gles] perf-sync sites`: engine-thread waits by GL function (calls, ms) per report;
- `[d3d8gles] perf-other draws by format`: the untagged draws by vertex format and primitive type;
- `[GX-PERF]` every 5 s in a match: client and logic ms per frame, fps, allocations per frame and KB
  (counted in the engine's global new -- which, note, zero-fills every allocation), heap in use.

### Performance Guard (owner's rules)

GXPerfGuard replaces the 22/10 tick-time gate (warning at a logic tick > 18.2 ms, kick at > 20 ms
for 10 s in any game) with frame-rate rules: a translated warning at 50 fps or below; 30 seconds in
a row at 45 fps or below in a multiplayer match leaves it (MSG_CLEAR_GAME_DATA, as the old gate did)
and counts a violation in Options.ini (GX_FPS_Violations); with 3, GeneralsOnline lobbies for more
than 4 players cannot be joined, hosted or grown by a map change; 3 multiplayer matches for at most 4
players played to the end without a kick reset it (GX_FPS_CleanMatches). The first 15 s of a match
and any second containing a frame over a second long (the app paused) never count; skirmish and
replays are never kicked. The 20 s freeze disconnect stays. The lobby limit is in the engine (the
lobbies are the game's own menus; the launcher never sees them). Texts in the built-in table and the
12 language packs.

Review (engine-reviewer) before the build was used: lockstep clean (MSG_CLEAR_GAME_DATA is the
engine's normal leave, seen by every peer on the same frame; no kick during loading, the score
screen or while the app is in the background, where GameEngine::update does not run). Fixed: a
refused host left SetLobbyAttemptHostJoin set and the lobby screen frozen (also on the existing
no-lobby-interface return); the thresholds now scale with the frame limit in force (the 30 Hz
engine renders 30 fps offline by design, which would have kept the warning up all game);
victory/defeat read in multiplayer only (no local slot in a campaign); no kick once the match is
decided; players counted without observers; a clean match needs two or more humans, no sandbox and
3 minutes of play. Not covered: QuickMatch joins (lobby size unknown when joining).

## 05/11/2026 -- Flux Build v1.3.9-test7 (Indicators pack online, render-thread waits, text pages)

### Leikeze Indicators pack: "This game's data differs from yours"

The owner's test6 log shows the cause, and it is not a checksum over CommandButton.ini (that INI,
like MappedImages, ControlBarScheme, InGameUI and CommandMap, is loaded without the INI checksum):
`community patch not mounted: a mod is installed (!HotkeysLeikezeIndicatorsZH)`, and then the lobby's
`ini_crc=2180732466` (the patch's INI set) against the local `4272612339` (vanilla). Any '!' archive
with a Data\INI file counted as a data mod, and a data mod keeps the patch out.

Not every interface INI is equal, which two rounds of engine review made plain (the first version
was a name rule, the second a lenient parser):
- MappedImages, ControlBarScheme, InGameUI and CommandMap are read by the client only. They pass when
  they hold no other block type: INI::load runs whatever block it finds in any file, so an InGameUI.ini
  carrying a Weapon block is a data mod.
- CommandButton is outside the checksum, but the simulation reads it (Object::canProduceUpgrade on
  every queued upgrade, AIUpdate, the skirmish AI, scripts), and a '!' archive's single
  CommandButton.ini masks the patch's whole split CommandButton\ set. A name rule would have let a
  pack that changes a button's Upgrade or Command into a lobby and desynced the match; a pack missing
  one of the patch's buttons would have stopped its CommandSet from loading. So a '!' archive's buttons
  pass only when they are the patch's with other pictures: every patch button present, and the eight
  fields the logic reads (Command, Options, Object, Upgrade, WeaponSlot, MaxShotsToFire, Science,
  SpecialPower) read the same -- one-token fields by their first token (retail's
  `WeaponSlot = SECONDARY TERTIARY` is SECONDARY to parseLookupList), Object/Upgrade/SpecialPower/
  Science case-sensitively as the game looks them up, "None" as no template.
- The files are read the way INI.cpp reads them, and anything not fully understood fails: ';' is
  the only comment ('//' is not), '=' is one more separator (`Object X` is a field), block and field
  names are case-sensitive, a header inside an open block, an unknown field, another block type, an
  unterminated block, or no patch buttons to compare with -- each makes the archive a data mod, as
  before. So do the things INI.cpp reads differently from a line split (a line of 1028 characters or
  more, which readLine continues on a "new" line even after a ';'; a NUL byte), an empty `Options =`
  (parseBitString32 keeps the earlier bits), a subfolder under CommandButton\ (loadDirectory reads it
  after the folder's own files), and buttons the patch does not define (map scripts and map.ini
  CommandSets find buttons by name). The log names the reason (`[gxbig] ... counts as a data mod: ...`).
- Data\<Language>\ INI in a '!' archive (CommandMap.ini, HeaderTemplate.ini, Language.ini) also go
  through INI::load outside the checksum: they pass only when they hold no block but those three.

### Render-thread waits (from test6's perf-sync sites)

- **GL name pools** (`gxGenPooled`, 4.5-9 ms per refill, several per 5 s in the menus): a sync for 64
  names whenever a pool ran dry. A pool at 96 names now queues a refill of 256 like any other command;
  the render thread writes them into a staging array and the engine's thread takes them on its next
  glGen. It waits only if the pool empties before the refill ran.
- **Index stream renewal** (`glMapBufferRange`, 1-6 ms): the next 4 MB stream is created and mapped
  through the queue (gxrt::mapBufferAsync) once the current one is half full; renewing it is a swap.
  A queued next stream is given back if the persistent path is turned off (driver refusal).
  The persistent vertex copies still map synchronously, but only when a dynamic buffer needs a new
  copy (`new-copies`, a handful per session).
- **Shader cache**: not a bug. `progcache load=2 save=0` with `programs built=2 (2 cached)`: both
  programs came from the cache, so there was nothing to save.

### UI text pages

The shared glyph-page pool was working (`[glyphpool] hit=5049`) and overflowing: `salvage_full=707`,
`miss=801` with the pool empty. A closing menu frees hundreds of labels at once; 32 pages were kept and
the rest destroyed, and the next menu created them again (created=708 deleted=667 in one visit). The
cap is now 512 pages within 4 MB (8 KB per 64x64 A4R4G4B4 page).

### Overlay freeze and kicks

- **Overlays froze the game.** On Android any window drawn over the game (a Discord or Telegram
  bubble, a call's heads-up screen, the notification shade) takes focus, and WINDOW_FOCUS_LOST set
  the mobile pause gate, which skips the whole engine update -- render, logic and network -- while
  the game was still visible with a valid surface. In a multiplayer match no commands left the
  phone, so the other players' disconnect timers ran out: a cause of the "random kicks". On Android
  only the background events pause now (iOS keeps focus-loss pausing; its layer needs it).
  Review (engine-reviewer) caught the consequence: with focus loss no longer pausing first, the
  background events arrived while the engine was still rendering, and the "transition frame" rule
  (render once more after the pause starts) then ran a frame with the GL context already released --
  every GL call a no-op, enough to turn the persistent-buffer path off for the session. On Android the
  background now pauses at once; the frame before it was a complete one. Under an overlay the game's
  audio keeps playing now (it used to drain and stop with the paused engine).
- **Coming back from a pause left the match.** The 20 s freeze gate (GameEngine.cpp) measured the
  first frame after a background pause as one frame of the whole pause, so a 20 s phone call ended
  the match -- skirmish too. Pause time no longer counts (GXLifecycle.h: a serial the pause gate
  bumps), and the gate runs in multiplayer only.
- **Why a match ends, in release builds** (`[GX-DISC]`): the disconnect screen coming on, a slot
  timed out or voted out, a disconnect command and who sent it, each vote. The DEBUG_LOG lines beside
  them exist only in debug builds. The test7 match itself ended normally (all five peers "closed by
  app ... Disconnecting Gracefully" when the owner left), so the next kick will be explained by these.

### Render thread

- **Dynamic vertex-buffer copies** (`glMapBufferRange`, the largest wait left: 24 waits, 291 ms,
  up to 113 ms in one, in the match). When every copy of a dynamic buffer is still in use by the GPU,
  a new one was created and mapped with a sync. Now creating one also queues the set's next copy
  through the render queue (create + gxrt::mapBufferAsync); the next time every copy is busy the
  spare is taken without a wait, from a set's second copy on (most sets never need a second, and a
  spare for each would double their memory). `perf-opt ... new-copies=N (M from spares)` shows it.
- Not changed: `glReadPixels` twice per match is GeneralsOnline's match screenshot (uploaded with the
  match data); the 262 untagged draws per frame are the stencil shadow volumes (D3DFVF_XYZ), whose two
  passes are required (LESSON-gles-upscaler-and-frame-pacing.md) and cheap; the ~200 ms of shader
  setup is at match load.

## 11/11/2026 -- v1.4.4-community 12184: edge scrolling for a real mouse

LookAtXlat already has the PC's screen-edge scrolling (SCROLL_SCREENEDGE, 3 px), gated on Android to the
launcher's mouse/touchpad mode because a finger can start it but never end it. A real Bluetooth/OTG mouse in
the normal touch mode was blocked too. Now canScrollAtScreenEdge also allows it while the hardware mouse is
the pointer (GXHardwarePointerActive: set by its events, cleared by a finger-down), and a finger-down ends
a running edge scroll (SDL3Mouse::gxFingerTookOver -> LookAtTranslator::stopEdgeScrolling). Fingers and
the two-finger camera never set the flag. Camera only.
Review (engine): the existing no-finger guard (enforceNoPointerScrollWithoutFinger) cancelled the scroll 3 s
after the mouse stopped moving, so a mouse resting at the edge stopped -- it now also exempts
GXHardwarePointerActive. With that exemption the stuck-scroll cases had to be closed: every finger-down already takes the pointer over (gxFingerTookOver, any time), (-1,-1) "no pointer" never starts an edge
scroll outside pointer mode, a stylus (SDL_PEN_MOUSEID) never sets the flag (its old 3 s mouse handling is kept -- dropping it
left pen clicks in the buffer to be replayed later), and leaving the window or unplugging the mouse
(SDL_EVENT_MOUSE_REMOVED, also clears the flag) stops the edge scroll. Known limit: Android's SDL sends
neither of those two events, so after an unplug the camera scrolls on until the next finger-down.
