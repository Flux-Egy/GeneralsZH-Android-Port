## 2026-10-01: Fewer GL calls per draw on the GLES backend

The old Mali phone throttles within minutes (two big cores, 2050 MHz falling to 1300-1800 MHz,
logs-39), so the remaining lever is less work per frame. After base-vertex draws (on by default on
Mali since logs-40: 8.9 -> 7.3 GL calls per draw) the largest per-draw cost left is uniforms:
~3.4 calls per model draw and ~2.4 per particle draw (`[d3d8gles] perf-state`).

- The world matrix was uploaded on every draw. Uniform values live in the program object, so each
  `ProgramInfo` now remembers the last world matrix it received and skips an identical one --
  particles and the further passes of one mesh repeat it. perf-opt reports sent vs. skipped.
- Material (three vec4) and lights (global ambient, count, and per light type, direction,
  position, diffuse, ambient, attenuation: eight calls) are packed into `uMat[3]` and `uLit[22]`,
  one `glUniform4fv` each; only the lights in use are sent. Lights change on ~15% of model draws,
  since every object gets its own nearest lights. The shader reads the packed layout (per light at
  `2 + 5i`). Program binaries are keyed by source hash, so the cache rebuilds itself.
- Uniform arrays over 64 bytes travel inline in the render thread's ring (`Blob<352>`) rather than
  through a heap allocation per call.

logs-41 (packed uniforms): 6.2 GL calls per draw (8.9 two builds ago), model uniforms 4.0 -> 2.3
per draw, particle uniforms 2.4 -> 1.2, 63% of world matrices skipped as already in the program,
lighting looked right. Yet at the same clock and temperature as logs-39 (1860 MHz, 62 C) fps went
only 43 -> 44 and render-thread time per draw stayed ~22 us: the cost is not in state calls but in
the draws themselves or in waiting for the GPU. `[d3d8gles] perf-gpu` now splits the render
thread's time into draw calls, swap (which blocks when the GPU is behind), uploads and the rest,
and reports GPU time per frame from GL_EXT_disjoint_timer_query when the driver has it (a
TIME_ELAPSED query from one swap to the next, read a few frames later, never waited on). The busy
counter is also accumulated while the render thread never catches up, which read as zero before.

logs-42 (render-thread split + GPU timer): the menu battle on High is GPU-bound on the old Mali
phone. Median frame 23.3 ms; GPU time per frame 30.6 ms (TIME_ELAPSED from swap to swap -- above
the frame time because Mali overlaps one frame's fragment work with the next one's vertex work);
the render thread spends 5.2 ms a frame blocked in the swap, 8.2 in draw calls, 3.5 in uploads and
5.7 in the rest. That is why cutting GL calls per draw by a third barely moved fps.

Render resolution in the launcher (Graphics > Render Resolution, 50-100% in steps of 5). The
fill-rate cost of a tiler scales with pixels, and the engine already renders at a resolution below
the screen's through its pillarbox pass (an offscreen target stretched to the screen with bilinear
filtering, touch remapped through the same rect) -- the path a smaller resolution from the game's
own Options takes. The launcher saves `GXRenderScale` in Options.ini and clears a saved
`Resolution`; SDL3Main.cpp, where it already reads Options.ini before injecting -xres/-yres,
renders at screen x scale (aspect kept, so no bars) when the player has not picked a resolution in
the game. 75% is ~56% of the pixels. The interface keeps its size: widget geometry is a ratio of
the resolution (see the removed "Interface Size" note in SetupActivity), only sharpness changes.

Snapdragon Game Super Resolution 1 for the pillarbox upscale. When the game renders below the
screen's resolution, DX8Wrapper::Pillarbox_End() stretches the offscreen frame to the screen with
one textured quad, bilinear until now. On the native GLES backend that quad is now drawn with
SGSR 1 (single pass: a 12-tap Lanczos-like edge-adaptive upscale plus sharpening; textureGather,
so ES 3.1): the engine brackets the draw with `d3d8gles_SetUpscaleBlit(1, srcW, srcH)` / `(0)`, and
drawCommon swaps in the SGSR program for that xyzrhw draw. Its vertex stage reproduces the
generated xyzrhw vertex shader, so the quad lands where the bilinear one did; the fragment stage
is Qualcomm's `sgsr1_shader_mobile.frag` (BSD-3-Clause, github.com/SnapdragonStudios/
snapdragon-gsr, RGBA mode, threshold 8/255, sharpness 2) with only its input names adapted and
`#version 310 es`. It falls back to bilinear when the program cannot be built, and under DXVK.
The launcher's Render Resolution card has a "Snapdragon GSR upscaling" switch (on by default),
saved as `GXUpscaler = gsr | bilinear` and passed to the engine as GX_UPSCALER by SDL3Main.cpp.
It applies to any resolution below the screen's, including one picked in the game's Options.

Virtual backbuffer instead of the pillarbox on GLES. The owner's report on logs-45/46 was worse
than the samples suggested: the intro logo stuttered on its first frame and could not be skipped,
the menu froze on its first frame with button labels missing, everything flickered. The pillarbox
switches an offscreen target in after the pre-render passes and out at End_Scene, so anything
drawn or presented outside that window (videos, load screens, nested Begin/End_Render) misses it;
on GLES that path has evidently never been sound. Rather than chase every such path, the
translator now owns it: `d3d8gles_SetVirtualBackbuffer(w, h, gsr)` makes "the backbuffer" an FBO
of the game's size (colour texture + its own depth-stencil), so every draw to the backbuffer --
scene, UI, videos, loading screens -- lands there; present() stretches it over the whole window in
one full-screen-triangle pass right before the swap, with SGSR 1 or bilinear, then rebinds it and
drops the cached GL state. DX8Wrapper::Pillarbox_Setup() on GLES asks for it whenever the game is
smaller than the window and returns without a pillarbox (DXVK keeps the pillarbox). A viewport
larger than the virtual backbuffer (the engine still knows the window's size) is taken as the
whole of it. Touch: with no pillarbox but a game size other than the window's, the finger's share
of the window is its share of the game (handleTouchEvent and the entry-field hit test).
The pillarbox-blit SGSR hook and the [GX-UPSCALE]/[GX-PBFRAME] diagnostics are removed.

Upscaling the way a PC game does it. logs-47 (virtual backbuffer, 75% + SGSR) ran the menu battle
at 57 fps median, 45 in the bottom 10%, against 44-50 at full resolution -- but the owner pointed
out that the launcher's percentage slider only lowered the game's Resolution, which is what picking
a smaller resolution in the game's own Options already did: the game saw the smaller size. On a PC
the game stays at the monitor's resolution and FSR's mode decides how much smaller the GPU renders.
Now the same here. The virtual backbuffer has two sizes: the engine's (the game's resolution --
viewports, 2D coordinates, touch, the Options screen all stay in it) and the rendered one, the
engine's times the mode's scale. Only `targetRect()` knows the second: every glViewport and
glScissor into the virtual backbuffer is scaled there, both edges rounded separately so adjacent
rectangles stay adjacent; the shaders keep working in the engine's pixels (uViewportPos), so
pre-transformed 2D needs nothing. Render targets (water, shadows, screen filters) are untouched.
present() stretches the rendered texture with SGSR. The launcher's "Render Resolution" slider and
GSR switch are replaced by an "Upscaling (Snapdragon GSR)" card: Off / Ultra Quality / Quality /
Balanced / Performance, FSR 1's names and scales (77/67/59/50%), saved as `GXUpscale` in
Options.ini, passed by SDL3Main.cpp as GX_UPSCALE to DX8Wrapper::Pillarbox_Setup(). The slider's
lowered Resolution is put back to the screen's full size on the first pick. The interface is
rendered at the reduced size too (one target for the whole frame); upscaling the scene alone and
drawing the 2D at full size would need the split point between them, left for later.

The interface at full resolution. The owner confirmed the upscaler modes work and asked for the
interface to be kept out of them. W3DDisplay::draw() now calls DX8Wrapper::Upscale_Scene_Begin_UI()
between drawViews() and TheInGameUI->DRAW() (the spot the parked Pillarbox_End/Begin_UI pair was
meant for). On GLES that is d3d8gles_UpscaleSceneNow(): when the scene was rendered below the
game's resolution and the game's resolution is the window's, the virtual backbuffer is stretched
into the window with SGSR right there, the window's depth/stencil cleared, and "the backbuffer"
becomes the window until present -- so the control bar, text and cursor draw 1:1 at the screen's
resolution. present() skips its own stretch for such a frame and rebinds the virtual backbuffer
for the next. Frames with no 3D view (videos, load screens) still stretch whole at present.
In-world 2D (health bars) is drawn inside drawViews() and stays with the scene.

### Online: the joining player never had a TURN relay (issue #31, "Mesh is not fully connected")

A player on a Poco X3 Pro cannot start an online game with anyone: the full-mesh check reports
both directions unconnected. Reading the join path: the joiner builds its mesh *before* the join
response (deliberate since 13/09 -- the service's START_SIGNALLING arrives ~78 ms before the HTTP
reply and was dropped without a mesh), so the constructor set empty TURN credentials; the response
then stored the real ones and nothing passed them on. Every connection of the joining player, the
first and each retry, was negotiated with no relay on its side. The host builds its mesh after
CreateLobby's response and was fine; the upstream PC client has the same joiner defect.

Fix: the joiner's mesh holds signalling (`NetworkMesh::AwaitTurnCredentials`) -- outbound
START_SIGNALLING requests are queued, inbound signals stay buffered in the WebSocket, since an
inbound connection takes its configuration when it is created -- until the join response hands
over the credentials (`ApplyTurnCredentials`, which sets the global TURN user/pass lists and
releases the queue). No response within 5 s releases it without a relay, as before. Log lines:
`[NGMP] Mesh holding signalling...`, `Mesh TURN credentials applied (... N deferred ...)`.

Not confirmed on the reporter's device yet; asked for a log with the online network log on.

### Text fields edited in an Android EditText: cursor, selection, copy, paste

The game's entry gadget only appends and deletes the last character, so on a phone a typo three
words back meant deleting three words, and nothing could be pasted. Rather than rewrite the gadget
(every text field of the retail UI), a tap on an entry field now opens an EditText bar at the top
of the screen (the keyboard covers the bottom) and the field mirrors it
(`SDL3Device/GameClient/AndroidTextEditor.cpp` + `TextEditorBar.java`):

- the bar opens with the field's text, its length limit (`maxTextLen - 1`, what the gadget accepts)
  and kind (password, digits only);
- each change replaces the field's text through `GWM_IME_CHAR`, so the gadget's own filters apply
  and its owner hears `GEM_UPDATE_TEXT` as for typed text; control characters (a pasted line break)
  are dropped, since `\r` would end the edit;
- Done/Enter or the bar's OK sends `VK_RETURN` (chat sends, the password popup joins); Back keeps
  the text and closes the bar; the field losing focus closes it; another field taking focus
  while it is shown takes it over;
- calls from the UI thread are queued with a serial and applied by `pump()` on the game thread,
  so a late change for a field that has since lost focus is dropped.

The bar replaces SDL's hidden text field on Android only (iOS keeps the SDL path). It has no
strings of its own (the button is `android.R.string.ok`), so there is nothing to translate.

### GeneralsOnline: the service's source, and the first batch of upstream client fixes

The GeneralsOnline team's service is public (`GeneralsOnlineDevelopmentTeam/services`, C#/.NET).
Read against it:

- **Issue #31 confirmed server-side.** `LobbyController` joins the player to the lobby (which sends
  `START_SIGNALLING`) and only then asks the TURN provider for credentials, over HTTP, for the
  reply. The joiner always started signalling without a relay.
- **Our mesh-check reply was a "legacy" one.** It carried no `mesh_check_id`/`attempt`; the
  service counts such a reply for the first attempt only and, while any member is legacy, never
  runs the retry attempt (`FullMeshCheckProtocol.ShouldRetry`). A lobby with this client in it
  got one chance to connect. The reply now echoes both and adds `connecting_map` (peers still
  negotiating, which the service waits for).
- **Device identity.** The service expects the PC client's `YY`/`ZZ` suffixes on the three HWID
  fields and files every other login for manual anti-cheat review (`AcReviewsProbes`), three rows
  per login. No automatic ban follows from it. Not faked here: that is for the GeneralsOnline team

## 03/10/2026 -- Online sessions died after fifteen minutes: session renewal

Owner's log 52 (02/10), read for its network side: signed in at 18:30, and from 18:45 on every
request -- lobby list, player stats -- came back 401, 826 times until the game was closed, with no
word to the player. The lobby simply stopped changing. The GeneralsOnline service issues session
tokens for fifteen minutes (`ExpiresInMinutes_Session: 15` in its appsettings); the PC client
renews them every ten with its refresh token (`RefreshToken()` in `OnlineServices_Auth.cpp`), and
this port took its session from the launcher and never renewed it. Any online session longer than
fifteen minutes -- a lobby wait, or a match, whose result is posted at the end -- lost its sign-in.

Renewal is ported, with one difference forced by the launcher. Refresh tokens are single use: every
renewal rotates it and the server accepts only the newest (the previous one for five more minutes,
`TokenRevocation.cs`). Two holders of one refresh token, the launcher and the engine, would
invalidate each other, so the session marker file is where the newest one lives: the engine reads it
before every renewal and writes the rotated one back atomically; the launcher writes it there at
sign-in and reads it there (`currentRefreshToken`) before its launch-time refresh, the silent
re-sign-in and the diagnostics. A 1.3.0 launcher never wrote it to the marker, so for it the engine
reads the one in the launcher's own preferences file (same app, `shared_prefs/`) the first time and
the marker after that. 1.3.0's own launch-time refresh then fails as superseded and leaves the marker
alone, which it already did on any failure, and the engine renews from the marker.

The schedule follows the token's `exp` claim (renew five minutes before it), not a fixed ten
minutes after creation: the engine can receive a token minutes old, or expired (launch refresh
failed, game idle in the menu) -- in that case it is renewed before the WebSocket connects. A failed
renewal is retried every 30 s while the token lives; one that cannot succeed (or HTTP 423, a ban)
tears the online session down with a message to sign in again, through the menus' existing teardown
path, so never in the middle of a match.

Same log: a public lobby refused the join with 417 (anticheat) and the client printed the "account
already in the lobby" hint before "Anticheat mismatch"; the hint is no longer printed for 417.

## 04/10/2026 -- Issue #37: a dead UDP port 53 pushed the relay past the connect timeout

## 04/10/2026 -- Issue #33: the control-group panel ate touches, and "9" stopped working

## 04/10/2026 -- Campaign: mission 2 ran in shell mode under the main menu

## 05/10/2026 -- Mouse and touchpad mode (#39)

#39 asked for Winlator-style controls: a pointer moved like a touchpad, on-screen keys. The keys are
covered by the command-bar buttons (#25). The pointer is a launcher switch now, "Mouse and touchpad"
(Interface > Controls), off by default.

Found on the way: a connected mouse did nothing in the game on Android. `SDL3Mouse::
createStreamMessages()` is a no-op on touch platforms (so a stale per-frame position cannot fight
the touch layer), so a real mouse's events were buffered and never became messages -- the earlier
claim in #25 that a mouse "works as on PC" was wrong.

With the switch on (marker `mouse_mode` in the app's files dir, `GXMouseMode.h`, read once like
`GXLogging.h`):
- `SDL3Mouse::createStreamMessages()` runs the base one: a real mouse works as on a PC.
- Fingers go to `handleTouchpadEvent` instead of the native touch layer: relative motion (x1.6,

  pointer), tap = left click, second tap within 300 ms = double click, tap then touch-and-move =
  left drag (selection box), two-finger tap = right click, two fingers = `applyCameraPan` /
  `applyCameraZoom`. They are mouse events with their own id (`TOUCHPAD_MOUSE_ID`) in the same
  buffer as a real mouse's, so the game's own mouse handling answers them. A click on a text field
  re-arms the on-screen keyboard.
- Android draws a pointer only for a real mouse, so `SDL3Mouse::draw()` draws the touchpad's: the
  game's own cursor (attack, move, ...), its frames converted once from the decoded ICO surfaces
  into textures, scaled with the screen height; a plain cross if there is no cursor art.
- Edge scrolling is allowed again in this mode (`LookAtXlat::canScrollAtScreenEdge`): there is a
  pointer that rests, so the exit condition exists. The ability radius and the building ghost read
  the pointer, not the touch aim point (InGameUI, both games).

## 18/10/2026 -- Cross-play with PC turned off, at GeneralsOnline's request (engine update 3278)

A GeneralsOnline developer asked for Android-PC cross-play to stop: Android clients averaging
41-52 fps held lockstep games back for PC players at 143 fps, and 3 of 9 test games desynced. The
owner agreed. Cross-play was always opt-in (the launcher's switch writes `gx_pc_compat.txt`, and
only then does `GlobalData::init` claim the PC executable's checksum), so turning it off means
making the engine ignore that marker.

The signed settings alone cannot do it. The claimed number comes from the marker's content first,
then from the checksum the launcher computed when it installed the community data package
(`pc_exe_crc_seed.txt`, since 27/09), and only then from `pc_exe_crc` in the settings -- so for
nearly every cross-player the settings are never read.

The engine now honours the marker only with `pc_crossplay=1` in the signed settings, which they do
not carry; without it the client reports its own checksum and meets only Android clients. The
launcher hides the cross-play card on the same key. For 1.4.0 without a new APK: engine 3278 =
the release tree (576e2265b) + the GPU timer change of engine 3277 + this change, branch
`hotfix-1.4.0-crossplay-off`, built with the release's own `build-dual-hz.sh`. Settings: `pc_crossplay`
"0" and `pc_exe_crc` "1", a number no PC client has, for engines that would still read it.

1.3.0 gets 3278 too: every library in its APK except the two engines is byte-identical to 1.4.0's
(compared file by file), so the same `requires_libs` match both. (The 3277 entry above says new
1.3.0 installs would not get that engine; they did, for the same reason.) Releases up to 1.2.2
have neither the updater nor cross-play -- their checksum was always Android's own. Not reached:
installs with automatic updates off that never press Check for updates, and other builds of this
port. The GeneralsOnline developers were told so, for refusing them on the server.

Built in a fresh container (meson 1.12.1 from pip, glslang 15.1.0 and the `references/fbraz3-dxvk`
submodule at the release's pin; fonts and the default Turnip driver staged from the 1.4.0 APK,
since their download URLs now answer 403/404). Against the 1.4.0 APK: ANGLE, libc++, adrenotools
and both DXVK libraries are byte-identical; SDL3, SDL3_image, gamespy and the four hook libraries
differ only in `.note.gnu.build-id` (a hash of the build path -- identical once it is removed);
OpenAL is configured differently but exports the same symbols. The engine's `NEEDED` list and its
777 imported symbols are the release engine's, and its strings differ from 3277 only in the build
date, the commit hash and the new `[GX-CRC]` line. So `publish-update.py` got
`--requires-from <released APK>`: the engine files come from the new build, `requires_libs` from
the files players actually have (the same digests 3277 was published with).

Published as manifest serial 13 (engine 3278, `pc_crossplay=0`, `pc_exe_crc=1`). Signing first
failed: GitHub had disabled the workflows of this fork ("Workflows on this fork have been
disabled"); the owner re-enabled them and disabled the inherited "GeneralsX CI", the only one with
a `push:` trigger. The signature verifies against the launcher's public key. Owner's check on
release 1.4.0: the launcher downloaded engine 3278, and in the lobby list every PC game is greyed
out as incompatible while `[Android]` games stay joinable.

### Feature switches, for this and the next one

Switching cross-play off took an engine build because the old engines had nothing to read. Now
there is a general switch: `GXRemoteConfig::enabled(name, default)` in the engine and
`UpdateManager.featureEnabled` in the launcher read `name=1`/`0` from the signed settings. Every
switch is listed in `update/features.json` (default, what it does, which builds read it, which do
not, companion keys), and `scripts/update/features.py list|on|off|check` sets them in
`update/config.json`; `publish-update.py` refuses a value other than `0`/`1`. `pc_crossplay` is
the first. Turning it off also sets `pc_exe_crc` to 1; turning it on demands the PC number.

Two holes closed with it. A settings-only publish dropped the engine: the branch is replaced whole,
so after a later settings change a player who reinstalled the APK would have run the APK's engine
again -- for 1.3.0/1.4.0, one that still cross-plays. `publish-update.py` now carries the published
engine and its files over (checked against their digests) unless `--drop-engine`. And the next
launcher fetches the signed settings when the multiplayer screen opens even with "Check
automatically" off: that switch holds back downloads, not a few lines of settings that decide what
is allowed online.

## 18/10/2026 -- A test channel for over-the-air updates

The updater had one channel: the `updates` branch, one engine slot, read by releases and test
builds alike. A test engine could only be shipped there by taking the slot from the release engine
(after 3278, the one that keeps cross-play off) and offering it to players whose libraries match --

## 18/10/2026 -- Mods and language packs together: a mod's own text above the pack

Players with mods saw `MISSING: 'CONTROLBAR:ToolTipUSABuildFortif...'` (Shockwave, 4PDA) and, with a
language pack chosen, MISSING "everywhere": the pack (`.str`) translates Zero Hour's labels only, and
the one fallback table was the game's `generals.csf` in the game's language -- for a Russian install
with an English mod, a table without a single label of the mod.

system has, for the pack's language, the game's and English, highest priority first. A copy is a
mod's when it is a loose file or comes from a `!` archive (the rule `loadMods()` uses for the
community patch) or `-mod`; the first copy that is not, is the game's. From them:

  the pack's language when the mod ships that language;

## 18/10/2026 -- LAN games over virtual-LAN VPNs (MiniLAN, Tailscale, ZeroTier)

Playing LAN with friends who are not on the same Wi-Fi needs a virtual LAN: a VPN that gives every
player an address on one shared network. On Android those VPNs are `tun` interfaces, and the LAN IP
list skips `tun*` (so a privacy VPN or mobile data never becomes the lobby address). The virtual LAN's
address therefore never showed under Options -> IP Address, the lobby bound to Wi-Fi, and its
broadcasts left through Wi-Fi only, so players on the virtual LAN never saw the game.

- `IPEnumeration` also lists a `tun*` interface when its address is in the shared address space
  100.64.0.0/10, the range virtual-LAN VPNs use. Other VPN tunnels and mobile data (`rmnet*`,
  `ccmni*`, which can use 100.64/10 too) stay excluded.
- The list is sorted, so with a virtual LAN connected its 100.x address sorts before 192.168.x and
  becomes the lobby address; without one nothing changes.

## 19/10/2026 -- PR #54 (Uss15) taken into 1.4.1, with the default address kept on Wi-Fi

The owner wanted PR #54 in the release. Thought through before merging:

- The idea holds: with the LAN socket bound to the tunnel's 100.x address, Linux sends the lobby's
  limited broadcasts out of the interface that owns that source address (the tunnel), and unicast
  to a 100.x peer leaves with the tunnel's own address, which the tunnel accepts.

  list; Direct Connect by address works. VPNs made for LAN games (MiniLAN and the like) carry them.
  ZeroTier usually hands out 10.x/172.x/192.168.x, outside 100.64/10, so it is not covered.
- The PR made the tunnel address the first one -- and the first address is every default (LAN
  lobby, Options, Direct Connect, OptionPreferences). A phone running Tailscale for anything else
  would then host and look for LAN games inside the tunnel, invisible to friends on the same Wi-Fi.
  So the virtual-LAN addresses now go to the end of the list (IPEnumeration.cpp): Wi-Fi and cable
  stay the default, the 100.x address is offered under Options -> IP Address, and with no other
  network up it is the default anyway.

## 28/10/2026 -- Flux Build v1.2.6-personal (Crossplay Map CRC Baseline Fix: Clear/Refresh the Lobby CRC)

**Symptom:** A PC (Steam) host and an Android v1.2.5 client completed the custom-map transfer

**only** from the client's own `MapCache` in `NGMPGame::SyncWithLobby()`. NGMP never transmits
the host's map CRC: the lobby payload has `ExeCRC`/`IniCRC` but no `MapCRC`, and the
`START_GAME` packet is just `{"msg_id":13}`. The same lobby had changed map from
`[RANK] Vendetta ZH v1` (231,317 bytes, CRC `0x7FD702FC`) to `fort thunder v3` while the client
did not have Fort Thunder. `SyncWithLobby()` took its `else` branch, which updated the map name

compared the new Fort Thunder file against the old map's CRC -- a self-comparison across time,
not a host/client difference. The received file was byte-complete and its CRC was correct.

**Fix:**
- **`NGMPGame::SyncWithLobby()` (`GeneralsMD/.../NGMPGame.cpp`):**
  - A cache entry is only a valid baseline when `m_doesExist` is set and, for a custom map,
    `CanSendMapFile(md->m_fileName)` can still open it. Official maps are exempt because they
    live in BIG archives.

    stops the previous map's CRC from surviving a lobby map change or a deleted cache entry.
  - Logs `[GX-MAP-XFER] lobby sync: map='...' cache=N file=N crc=0x........ size=N` once per
    change (not per lobby refresh).

  - Captures `hadMapBefore` for the local slot before `DoAnyMapTransfers()`.
  - If the slot went `hasMap=0 -> 1`, the client just received the host's file; the full-file
    `calcCRC()` result becomes the baseline (`setMapCRC(fullFileCRC)` / `setMapSize()`), the
    self-comparison is skipped, and the refresh is logged
    (`[GX-MAP-XFER] CRC baseline refreshed after transfer: 0x........ (was 0x........)`).
  - The launch summary now includes `hadMap`, `received` and `baseline`; a real mismatch is
    logged as `vs cached baseline` (not `vs lobby`), and the error text no longer claims the
    host's map was compared.
- **`ConnectionManager::processFile()` (`Core/.../ConnectionManager.cpp`):**
  - After a `.map` write, erase the live `TheMapCache` entry for that path. `MapCache::addMap()`
    returns early when the size matches and the CRC is nonzero, so a same-size replacement would
    otherwise keep the old CRC; erasing forces `updateCache()` to recompute the full-file CRC.
- **Strict constraints preserved:** no line-ending normalization (the map is binary and the raw
  CRC matched), no `calcCRC` change, and no changes to MTU, `NextGenTransport`, pacing,
  JSON/HTTP parsing, Graceful Fallback, QuickMatch/SSL, Touch Engine or PERF-GATE.

## 29/10/2026 -- Flux Build v1.2.9-personal (In-Game Chat Wire Format Alignment & UI Display Fix)
